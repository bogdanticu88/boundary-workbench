System purpose and scope

Orion is a proposed internal platform that helps engineers review synthetic PRs and investigate security findings in a sandbox. A harness coordinates workers and tools. The current request concerns design readiness before a connected pilot, not production authorisation.

Explicit assumptions

  • No production credentials or customer data.
  • All testing requires a target owner and written scope.
  • The platform is Microsoft-native; exact hosting and CI/CD choices remain open.
  • A central harness does not imply complete mediation.

Excluded from this assessment

  • Credit, underwriting or customer eligibility decisions.
  • Model training and fine-tuning.
  • Real penetration tests or legal authorisation of targets.
  • Supplier contractual assurance and implementation audit.

Reassessment triggers: new agents or tools, broader identities, production access, external communications, model/provider changes, persistent shared memory, new personal-data flows or increased autonomy.

Identity and execution risks

The two paths with the most direct access to source and credentials.

R01HighOwner: Identity and platform engineering

Service authority can exceed the requesting user’s scope

Scenario. A user requests a source file or finding belonging to another project. The harness invokes a tool using its service identity, which can access both projects. The backend validates that identity but does not check the requesting user’s project membership.

Business consequence. Disclosure of source code or security findings across teams. If write permissions are later introduced, the same path can permit unauthorised modification.

Current basis and gap

E01 and E02 describe shared backend access; no user-to-resource authorisation design is supplied.

The design identifies workload identities but does not specify how the initiating user and assigned task constrain each tool request.

Required design response

REQ01. Bind each request to the initiating user, project and assigned task. Enforce resource ownership outside the model before retrieval or action. Separate service capability from user entitlement.

Acceptance test. V01: a synthetic Project A user requests a Project B resource directly and through delegation. Access must be rejected before content reaches the model. Repeat with cached and guessed identifiers.

Closure evidence. A reviewed authorisation design plus negative integration-test evidence showing the relevant backend and delegated paths reject the requests.

R02HighOwner: Developer platform engineering

Untrusted PR code can reach execution credentials

Scenario. A contributor submits a PR containing a test or dependency installation hook. The harness schedules that PR workload on the testing worker, where a repository token or broker credential is available. The code reads the credential and attempts an unauthorised repository operation.

Business consequence. Credential theft, repository changes or lateral access, depending on the actual token scope. No production deployment path is assumed in this assessment.

Current basis and gap

E01 and E03 place test execution and a repository credential in the same proposed worker environment. This is a fictional design declaration, not an observed exploit.

The sandbox boundary, mounts, egress and credential injection strategy are not specified. “Containerised” is not accepted as sufficient evidence of isolation.

Required design response

REQ02. Execute untrusted code in disposable constrained workers without platform credentials. Broker privileged operations separately. Restrict mounts, process privileges, network access and artefact promotion.

Acceptance test. V02: a harmless synthetic test attempts to read injected canary credentials, host-mounted files and disallowed endpoints. Confirm denial and corroborate with worker and target-system records.

Closure evidence. Reviewed isolation configuration, credential exposure inventory and repeatable negative tests for the explicitly scoped execution boundary.

Delegation and testing scope

Contain authority across workers and every target interaction.

R03HighOwner: Harness engineering

Delegation does not preserve the original task boundary

Scenario. The coordinator delegates a narrow investigation to a worker that has a broader standing identity. The worker performs a tool action outside the user’s project or task because the destination only sees the worker’s credential.

Business consequence. Actions are performed using authority that the initiating user did not grant. Attribution and containment become difficult across delegated work.

Current basis and gap

E02 and E04 describe task hand-off but omit how identity, scope and cancellation travel to a worker.

There is no specified rule preventing permission expansion, binding delegates to a task, or rejecting fabricated delegation metadata.

Required design response

REQ03. Define authenticated delegation with explicit task/resource scope, expiry and destination. Require the destination to enforce the narrowed authority and reject unsupported or expanded grants.

Acceptance test. V03: attempt to substitute a different resource, expand the allowed operation, reuse an expired delegation, and invoke the worker directly. Each unauthorised attempt must be rejected before an effect.

Closure evidence. End-to-end delegation design and tests covering both coordinator and worker enforcement, including a direct-call bypass attempt.

R04HighOwner: Security testing platform owner

Testing can escape the authorised target set

Scenario. A testing task starts at an approved synthetic URL. A redirect, discovery result or tool argument points to a different host or internal service. The agent follows it without rechecking the authorised target scope.

Business consequence. Unauthorised traffic or disruptive testing against an out-of-scope service. The report assumes no permission to test production or third-party systems.

Current basis and gap

E03 defines “sandbox targets” but does not define destination validation, redirect handling or authorisation records.

Target ownership, permitted techniques, rate limits and per-action scope enforcement are not specified together.

Required design response

REQ04. Record target-owner authorisation and permitted techniques. Enforce destinations, redirects and applicable name-resolution checks at execution boundaries. Apply traffic limits and an operator stop mechanism.

Acceptance test. V04: use two isolated mock endpoints. Redirect from the authorised endpoint to the unauthorised one and verify that the second receives no request. Include resolved destination changes and a delegated tool call.

Closure evidence. Authorised scope record, reviewed enforcement design, target-side negative test evidence and an exercised stop procedure.

Operational and data risks

Make uncertain outcomes and information handling explicit before live use.

R05MediumOwner: Harness engineering and operations

Timeouts and cancellation leave effects uncertain

Scenario. A sandbox action succeeds but its response is lost. The harness retries, or an operator cancels the parent while queued worker tasks continue. Duplicate or late effects occur after the operator believes work has stopped.

Business consequence. Duplicate sandbox changes, inconsistent findings and additional operational work. The rating must be revisited before financial, production or other high-impact writes are enabled.

Current basis and gap

E04 states cancellation is planned. Retry and partial-outcome semantics remain undecided.

The design has no defined cancellation acknowledgement, effect reconciliation, or rule for retrying an action with an unknown outcome.

Required design response

REQ05. Define effect classes, request identifiers, outcome reconciliation and a no-blind-retry rule for uncertain writes. Propagate stop/revocation state to workers and queues with documented race limitations.

Acceptance test. V05: inject a lost response after a synthetic successful write; inspect the target for duplicates. Cancel a delegated task with queued work and verify the documented acknowledgement and effect boundary.

Closure evidence. Documented execution semantics, fault-injection results and an operational procedure that states what cancellation does and cannot undo.

R06MediumOwner: Data owner and AI platform engineering

Prompts and traces can disclose sensitive source material

Scenario. A source file, test fixture or tool response includes a secret or personal information. The content reaches the external model or diagnostic trace without minimisation and is retained or made accessible more broadly than intended.

Business consequence. Disclosure through provider processing or internal logs. The sample contains synthetic data only; real-data impact cannot be rated confidently until data flows and access are known.

Current basis and gap

E01 proposes an external model endpoint and central traces. Content handling, retention and provider settings are not supplied.

Data categories, permitted destinations, trace access, retention and redaction responsibilities are unresolved.

Required design response

REQ06. Document the data flow and approved provider configuration. Minimise model inputs and traces, prevent raw-secret exposure, restrict access and define retention with the responsible privacy and supplier reviewers.

Acceptance test. V06: seed harmless canary values in synthetic documents and inspect provider-bound payloads and traces. Confirm expected removal, approved destinations, access restrictions and retention configuration.

Closure evidence. Owned data-flow and provider review, approved handling configuration and test evidence. Specialist review determines any additional privacy assessment needed.

G0 Offline prototype

Use synthetic content, stub tools and no live credentials. This permits development without granting access to real repositories or targets. Record the prototype owner and preserve design decisions.

G1 Connected sandbox pilot

Security reviews closure evidence for R01 to R04. R05 and R06 require either closure or a bounded, time-limited exception accepted by the authorised risk owner. A reviewer verifies scope, minimal access, monitoring, stop procedure and synthetic-data restrictions. An exception cannot authorise testing of an unapproved target.

G2 Production consideration

Requires a new assessment of actual data, business impact, production identities, supplier dependencies and operational readiness. G1 approval does not carry over automatically.

Minimum evidence quality

Each test record identifies the build/configuration revision, actor, resource, expected result, observed target effect, execution time, evidence location and limitations. A model’s statement that it refused an action is not sufficient proof that no effect occurred.
